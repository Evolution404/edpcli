# edpcli P0 性能基线 / P1 TUI 性能治理

日期：2026-10-08；基线源码：`e68776b` 工作区上的 P1 待提交改动。运行环境：macOS arm64，仓库 v2.5.0。所有测试均使用**合成备份或普通临时文件**，不枚举、写入或格式化真实 USB。

## 可复现入口

```sh
uv run --locked python scripts/benchmark-p0.py
uv run --locked python scripts/benchmark-p0.py --compare audit/performance/p0-baseline-20261008.json
```

默认输出 `target/performance/p0-current.json`，包含 CLI 帮助命令启动、备份目录冷热扫描（字节数/缓存命中/峰值 RSS）、文件镜像事务（计划/镜像/写/同步/读回/总耗时）、Inspect 的 1000 次文件扇区读取、模拟两个设备的扫描，以及 100/1000/10000 行 TUI 构建、缓存、排序、过滤、搜索和帧绘制。基线快照：`audit/performance/p0-baseline-20261008.json`。

`--compare` 是同一台 Mac 上执行的可选性能回归门禁：关键指标同时恶化超过 2 倍且绝对退化超过 5ms 才返回非零。噪声较大的共享 GitHub Runner **不会**据此自动拦截产品发布；基础解析/门禁判断逻辑由 Python 单元测试覆盖。

## P1 已实现内容与对比

1. **表格与搜索统一投影**：在扫描结果替换时，身份解析一次同时生成表格列及规范化的搜索文本；查询时不重复建立 `WorkspaceIdentity`，并对刷新重建添加回归测试。
2. **排序缓存**：表格排序每行只解析一次语义/数值排序键，保留既有总序关系、相同值及降序语义。完整未过滤列表的列宽直接复用原始投影；过滤时仍计算当前可见行的宽度。
3. **搜索索引**：备份筛选使用按行对齐的布尔掩码，避免为每次搜索构造 `BTreeSet`；设备列表每帧复用可见索引快照。
4. **概览缓存**：备份盘型计数缓存于列表刷新时，而不是每次重绘时扫描全部备份；按设备过滤数量复用已经建立的分组键。
5. **后台任务 UI 响应**：进行中的单飞后台任务存在时将 crossterm 轮询等待上限缩短至 25ms；空闲保持 250ms，运行中动画帧限速不变。此项是**轮询上限优化**，没有声称已实现跨线程的真正事件唤醒。

同一 Mac、10k 测试数据，在本轮列宽复用优化前后的对照：容量排序约 **28.21ms → 1.67ms**，8 字符搜索约 **65.65ms → 35.08ms**，绘制约 8ms/帧基本不变。首次构建由上轮基准约 237.92ms 增至 263.76ms（约 +10.9%），原因是预构建搜索语料的额外成本；后续如需继续降低首次进入耗时，可以考虑懒加载搜索语料，且必须比较首次按 `/` 的延迟。上述数字是一次主机测试，不作为跨机器性能保证。

## 不在 P0/P1 可得证据范围内

真实 USB 的枚举/权限提升、实际闪存写入吞吐、断电恢复、实体介质挂载以及完整互动 TTY 冷启动延迟仍需对应环境单独验收。本次基准与虚拟 HIL 不构成对真实 USB 安全与速度的结论。P2 批量 I/O 与流式格式化不属于本阶段，不得未经故障注入验证直接引入。
