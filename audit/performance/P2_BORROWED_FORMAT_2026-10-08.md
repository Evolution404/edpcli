# P2 格式化写入计划零复制与连续 I/O 评估基线

## 范围、实现方式与安全不变量

P2 保留完整稀疏文件系统元数据镜像及格式化内容验证。先前的 `write_sparse_filesystem_image` 将 `SparseFilesystemImage.sectors()` 的每个扇区 `to_vec` 再放入拥有所有字节和 owner 字符串的 `WriteTransactionPlan`。优化后的格式化提交阶段采用只读借用扇区列表，**不再生成第二份扇区数据**。

新 `execute_borrowed_data_transaction_observed` 与已存在的正式写盘事务共享 `execute_sector_transaction_observed`：写前同步、为所有 touched LBA 读取连续回滚镜像、数据写入、写后同步、逐扇读回、失败后完整回滚及读回验证。它在任何 I/O 前拒绝不严格递增/重复的 LBA、超过末端的 LBA 及协议保留 LBA0-12。镜像偏移在应用层独立进行检查，格式化写入/读回进度仍映射为 `FormatWrite` / `FormatReadback`。

**注意**：这是预生成稀疏镜像的**零复制提交**，不是“整个文件系统格式化器按需流式生成”。Fat16/Fat32/exFAT 的空镜像构造与文件系统一致性验证仍需要预先完成，保守格式化资源预算未降低，也没有取消回滚镜像。

## 测量方式

```sh
uv run --locked python scripts/benchmark-p2-format.py --samples 3
```

构建两个变体使用同一份合成稀疏格式化元数据：`materialized` 用旧 `WriteTransactionPlan` 加入扇区 Vec（但共享最新的事务执行器）；`borrowed` 使用新借用列表。分别在独立进程创建临时普通文件，然后执行完整读回事务。三个不同规模，每种模式运行三次。结果记录：`audit/performance/p2-format-20261008.json`。不触碰硬件磁盘。

| 扇区数 | 数据体量 | 计划准备 ms p50（旧→新） | 相对原始镜像构建后 RSS 增量 KiB p50（旧→新） | 事务执行 ms p50（旧→新） |
|---|---:|---:|---:|---:|
| 16,384 | 8 MiB | 3.19 → 0.25 | 10,928 → 256 | 78.88 → 76.58 |
| 32,768 | 16 MiB | 6.58 → 0.79 | 21,776 → 448 | 132.50 → 137.08 |
| 65,536 | 32 MiB | 12.92 → 1.40 | 43,440 → 832 | 253.02 → 252.74 |

指标来自同一 Mac 的文件镜像/操作系统缓存。RSS 为最大驻留内存高水位，不能解释为回滚镜像本身仅使用 832 KiB——某些已分配堆页会复用现有高水位。可稳健确认的变化是去除了格式化计划中的独立扇区 Vec + 字符串分配；不能依据上述时间宣称真实 USB 写入速度提升。

## 验证覆盖

- 格式化写前拒绝重复、不递增、越界及协议保留扇区，无任何介质 I/O。
- 与拥有完整数据的 `WriteTransactionPlan` 在镜像、同步、写入、读回和进度事件上行为一致。
- 写入过程中故障注入，能够对包含非连续扇区的完整 touched 集执行回滚和读回验证。
- 格式化 Fat16/Fat32/exFAT 的现有完整验证、加密/非加密路径、恢复后格式化与虚拟 HIL 门禁保持原有覆盖。

## 后续工作

连续物理 I/O 与批量写入应独立于零复制提交评估：普通文件上的 syscall/IO 合并不等于 U 盘能获得同等收益；在没有实体设备、USB 总线、断连及故障注入验收证据前，不应更改原始设备的高风险写入策略。
