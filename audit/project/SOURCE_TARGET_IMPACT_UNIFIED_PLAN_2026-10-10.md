# edpcli：25 种模式转换的来源数据影响与确认页统一收口计划

日期：2026-10-10（2026-10-10 晚间修订）；执行分支：`feat/native-4kn-wal-staging-20261010`。与 `MULTI_LOGICAL_SECTOR_FULL_ACCEPTANCE_PLAN_2026-10-10.md` 配套，**本文件对“容量变化、起点变化、分区拆并、数据迁移及确认页统计”具有最新优先级**。本文件是待执行方案，不是实现完成的证明。

## 0. 非协商边界与业务真相

1. 模式集合：`Plain / Mode0 / Mode1 / Mode2 / Mode3`，来源 5 × 目标 5 = 25 种；`Mode0=启动区+交换区+保密区`，`Mode1=二合一区+保密区`，`Mode2=兼容保留区+保密区`，`Mode3=启动区+交换区`；Plain 可能有多个 MBR 普通分区。Mode2 兼容保留区不是文件数据区，不纳入“来源数据丢弃/保留”统计。
2. **任意分区起点或容量变化，强制格式化重建**；不存在本迭代的原位扩容/缩容、文件级迁移、跨区域复制、跨模式明文/密文搬迁、文件系统合并或拆分。只改来源密码且原 FileKey 可验证、几何和加密语义不变时，允许仅 Rewrap、不格式化。
3. 其他不兼容（角色、分区类型、实际文件系统、加密开关/算法、FileKey 及 LCE 的兼容性）也必须重建或停止，不得称为“原样保留”。**用户明确要求保留且实际无法保留时 fail closed**，不得静默勾选格式化；目标模式本身必需的重建必须明确告知来源影响和用户确认后执行。空白、缺失、不可信的来源快照不能伪显示“来源数据丢弃：无”。
4. 不变的已验证分区应优先 PreserveOpaque/PreserveVerified/RewrapVerified；数据范围和对应 FileKey 透传，实际 write-set 与保留数据区不相交。保留状态必须由同一个最终 prepare 结果提供，TUI 不得自行推导另一套事实。
5. CLI/TUI、物理盘/虚拟盘共用 SourceSnapshot → TargetLayout → TargetProvisionPlan → NativeWritePlan → WAL → 结果验证；本次任务仅治理影响统计与显示，不重新实现磁盘写入。当前实体 U 盘**禁止破坏性写入**，未经新授权只使用只读审计、离线样本和专用 OS 虚拟块设备。

## 1. 统一的三层事实与影响计算

| 层 | 对象及唯一标识 | 负责回答的问题 |
| --- | --- | --- |
| 来源 | SourcePartition（来源 ID、模式、role/MBR 索引、start_lba、sector_count、sector_bytes、FS/加密/密钥证据） | 原来有什么用户数据区；哪个来源区受影响、哪个保留 |
| 目标 | TargetPartition（目标 role、start_lba、sector_count、FS、加密方式、FormatIntent） | 最终创建/格式化/保留哪些区 |
| 执行 | RegionDisposition + PasswordDisposition + 实际写集合及保留证明 | 能否透传/仅改密/必须格式化；有哪些密码操作、是否允许提交 |

**数据影响必须按来源分区 ID 去重，绝不能按目标区个数统计。** 例如 Mode1 的一个二合一区拆为启动区+交换区，来源仅有“二合一区”受影响一次，目标仍有两个分区需要格式化。来源“保密区”只在真实保留时报告为保留。

判定顺序：

1. 只读取并冻结来源快照。EDP 来源按原生 LBA0–12 协议解析出真实分区及 LCE；Plain 来源根据 MBR 的分区条目建立来源 ID 和范围。Mode2 特殊保留区不计用户文件区。不得从目标布局**反推**来源。
2. 求解目标各分区的原生 LBA 范围；用户修改起点/容量或模式导致起点/容量变化，进入 `Rebuild`，绝不尝试伸缩或搬迁。相邻区域随布局移动也独立判断。
3. 对每一个真实来源数据区建立 source→target 映射：只有目标真实处置为 PreserveOpaque / PreserveVerified / RewrapVerified 且来源 role、起点、容量、扇区规格和加密语义等条件一致，才能记为 **保留**；否则为 **丢弃（转换后原文件不可访问）**。用原始来源唯一 ID 去重，不能只按名称去重；展示相同名称的多个来源分区时加 P 编号以消歧。
4. 目标单独统计哪些分区 `Format/Create`；密钥操作单独统计 `Rewrap`（仅改密码封装）和 `InitializeNew/Rebuild`（新密钥或重建），不得一律说“密码变化”，也不得将新的交换区 FileKey 误认为用户手动改密。
5. 以上全部从一份不可变执行计划生成；显示计划与落盘计划一致性测试必须覆盖分区范围、加密设置、格式化位、FileKey 记录和写集合。若来源解析不可证实、范围不可信或转化状态不明，显示“待核验/无法确认”，阻止擅自宣称无数据损失。

## 2. 用户确认页固定显示契约

摘要字段依次为：

- `来源数据丢弃：二合一区`（警示样式；列**来源分区名称**，不写“1 个区域/2 个区域”等数字）
- `来源数据保留：保密区`（正常样式；同样只列来源名称）
- `目标格式化：启动区、交换区`（列真实目标分区名称，不写数量）
- `密钥操作：交换区（新 FileKey）` 或 `保密区（仅改密）`；按实际执行语义填写，非用户名密码变化计数

多个分区以 `、` 连接，全部无对应项才显示“无”。不存在或不能确认来源时必须区分“无”和“未识别/待核验”；Plain 来源多个普通分区用 `普通分区P1` 等真实编号。技术依据可展开显示 LBA、范围、原因，**摘要优先分区名，不重复显示目标区数量**。当前区域详情仍可按目标区域列表导航，摘要的来源视角不影响目标区域列表。

基准实例（Mode1 → Mode0，用户除模式之外不改配置）：

| 项目 | 必须显示 |
| --- | --- |
| 来源数据丢弃 | 二合一区 |
| 来源数据保留 | 保密区 |
| 目标格式化 | 启动区、交换区 |
| 密钥操作 | 交换区（新 FileKey） |
| 来源映射 | 原二合一区 → 新启动区 + 新交换区；原保密区 → 保密区（原样保留） |

若目标保密区的容量、起点或算法变化，则 `来源数据保留` 不得再出现“保密区”，而 `来源数据丢弃` 应包括“二合一区、保密区”。保密区被删除（例如转 Mode3）亦如此。反之同模式完全不变且所有来源区经验证透传：来源数据丢弃“无”，来源数据保留列全部来源数据区。Mode2 兼容保留区单列“协议保留区”于区域执行计划中，不冒充用户数据区。
