# P2/P3/P4 后续开发：深度审计与修订路线

审计日期：2026-10-08；代码锚点：`bec81c2537ebd467969b0fe3a4caeaea5f222c0b`（main / origin/main）。**本次只审计并修改文档，没有修改生产代码，也没有访问、写入或复原实体 USB 介质。**

## 1. 执行决议

原路线「先安全、再流式格式化、再性能门禁、再 TUI、再冗余」总体方向可理解，但**不足以直接据此逐项开发**。要调整为：

1. **S0：先补底层介质分类和格式化保护边界**（阻断项）
2. **S1：补齐故障注入、真实格式化内存剖析、测量与门禁**（先取证）
3. **S2：修复确定的内存重复路径，并进入有针对性的 TUI 任务流验收**（用户直接收益）
4. **S3：仅在真实数据证明收益之后，立项 FAT/exFAT 按需生成器**（条件启动，而非既定必做）
5. **S4：基于确认的重复代码和调用关系小步整理架构**（持续维护，不应搞大规模一次性清理）

**禁令**：没有真实介质授权与硬件 HIL，不开放 raw 设备连续批量写入；不通过删除回滚、降低读回范围、取消协议保留区或放宽资源预算来获得性能提升。

## 2. S0 代码证据、安全缺口与精确建议

### A. I/O 设备分类依据不充分（高优先级，尚未证明 UI 可利用）

- `src/diskio/device.rs:95-119,188-258`：`FileDev` 保存字符串 `path`，`max_contiguous_sectors`、连续读写和 `sync` 使用 `platform::is_raw_device_path(&self.path)` 判断介质。
- `src/platform/macos.rs:56-58` 只匹配 `/dev/rdisk`；`linux.rs:59-61` 只匹配 `/dev/`；`windows.rs:806-808` 依赖 `\\.\\PhysicalDrive` 路径前缀。别名、符号链接及特殊文件的路径不等于打开句柄的实际类型。`FileDev::reopen_rdwr` 还会重新依据路径打开句柄。
- `tests/diskio::device::contiguous_batch_tests` 通过**更改对象中的路径文本**模拟 raw 分类。它证明路径分支起效，但没有证明「路径表示为文件、实际打开块/字符设备」时也会拒绝批量 I/O。
- 上游保护仍有效：`src/application/target_session.rs:118-159` 对写租约、设备几何、重新打开后的身份复核负责；不能据此得出普通 TUI 已可轻易写错盘的结论。

**建议**：在打开或重新打开 **实际 File 句柄**之后分类：只有经平台认可、已验证的普通文件方可启用 `max_contiguous_sectors > 1`。原始磁盘、字符/块设备、未知类别以及获取元数据失败统一 fail-closed 为单扇区；`sync` 选择也应跟随可信介质类别而非文件名。跨平台抽象在 `src/platform/`，不在业务层硬编码平台原生细节。Unix 可以基于句柄 `metadata().file_type()` 的普通文件/块/字符设备语义，Windows 需验证文件句柄类型并为不明确场景强制单扇区。

**验收**：普通文件及其符号链接可按策略批量；普通路径别名到原始设备不得批量；打开前后文件对象改变或路径重新打开后发生变化须拒绝继续写入；多个设备路径别名一致地走正确 flush；真实写租约和设备身份门禁不变。真实设备的安全测试需要隔离 HIL，不能以对生产盘进行破坏性实验代替。

### B. 借用格式化事务保护范围小于 EDP 布局保留范围（高优先级，纵深防护缺口）

- `src/common.rs:5` 的 `METADATA_LAST_LBA = 12` 只说明协议元数据末扇区。
- `src/diskio/transaction.rs:348-386` 的借用数据事务只禁止 `lba <= METADATA_LAST_LBA`，**LBA13–62 没有被此接口独立阻止**。
- `tests/canonical_disk_layout.rs:80-104` 明确：EDP 设备 LBA13–62 为保留区，分区重叠应显示冲突。`tests/provision_transaction_write.rs:510-529` 借用事务的拒绝样例仅覆盖 LBA0、LBA12、乱序/重复/越界，缺少 LBA13、LBA62 负例。
- 正常用户路径还经过分区几何和范围规划，尚无证据表明该缺口可通过 TUI 直接触发介质破坏。

**建议**：构造不可混淆的分区范围/介质布局约束，让**EDP 格式化**在执行器入口验证 `start>=63`、终点不越分区/目标、全体 touched 扇区只属于明确可格式化范围。**Plain 分区使用其独立几何与分区表规则**，不能把所有写盘操作一概锁成 EDP LBA0–62 规则。LBA0–12 协议元数据仍使用带 stage 的专用授权写入路径。

**验收**：EDP 的 LBA12、13、62 均在任何同步/镜像/写入前拒绝，LBA63 合法；Plain 的有效最早分区扇区按自身布局规则测试；兼容保留区不可格式化；不改变 mode1 二合一分区明文与加密分区差异。

### C. 故障模型未覆盖所有高危路径

- `tests/provision_transaction_write.rs` 已覆盖批量写部分完成、读回内容被篡改和回滚恢复、阶段顺序、进度；`Virtual Disk HIL` 已覆盖跨平台主要 raw 虚拟磁盘路径。
- 尚需组合覆盖：**镜像读取中途失败、write_all 短写后进一步失败、写后 sync 失败、回滚写失败、回滚 sync 失败、回滚读回失败、设备重新枚举身份变化、磁盘容量变化、进程/系统中断**；部分已有单独测试，要审计交叉覆盖矩阵而非盲目重复造测试。
- 回滚是软件尽力恢复，不等于跨扇区的硬件原子事务；断电后无法声称一定能自动恢复。

**验收**：明确 EXIT_ROLLED_BACK / EXIT_INTERMEDIATE / 未写盘三类状态，报告指示用户何时必须停止使用/重插和恢复；虚拟 HIL 不触碰用户真实 U 盘。

## 3. S1：先测再改，纠正资源预算与基准解释

- `src/filesystem/resource_budget.rs:6-53`：`working_payload_bytes = image_payload_bytes * 8`，默认 payload 64MiB、working 512MiB。这个模型写明是保守记账，而非实测；P2 已减少多余复制，原来的「8 份」注释需在资源剖析完成后重新证实。**不可因省一次 Vec 就直接缩减预算或扩大受支持卷大小。**
- 之前 P2 文件基准是合成连续的 `SparseFilesystemImage`，不是实际 FAT16/FAT32/exFAT 的典型分布。`audit/performance/p2-format-20261008.json` 的 RSS 高水位差不能作为实际用户分区内存峰值的唯一证据。
- `src/application/provision/format_plan.rs:132-159` 同时建立明文验证镜像和物理镜像；加密格式化的 `src/provision/partition_format.rs:72-89` 再生成明文映射并变换，仍有真实重复分配。`src/application/post_restore/reinitialize.rs:120-145` 的重新初始化路径仍用 `sector.to_vec()` 构建单独事务计划，不应遗漏。
- `src/filesystem/fat16.rs:319-354`、`fat32.rs:457-499`、`exfat.rs:677-741` 构建了 BTreeMap；exFAT 还分配 FAT bytes、位图、upcase/root 缓冲。因此需分别量化总分配、高水位、构建时间、变换、验证和提交成本。

**测量矩阵**：实际格式化产物（非任意连续合成负载），按当前驱动**已验证几何范围**选择小、中、大容量；对 FAT16/FAT32/exFAT、Plain/EDP、明文/SM4 加密分别测构建、规划、镜像变换、写盘、完整验证和最高 RSS；同机、锁版本、重复多轮，保留 JSON、失败输出及软件/硬件环境。对不存在合法参数的组合标明“不适用”，不能强行构造不支持的卷。

**基准门禁**：正确性、读回与回滚是硬门禁；性能回归采用同机重复样本、统计波动区间及人工审查，不将 1 次样本或跨操作系统的毫秒阈值当硬性 CI 失败。可参考 P2 的 10.8% 镜像减内存和文件负载 4.17×/5.46×，但不外推实体 USB 或真实 FAT 格式化速度。

## 5. S3：流式格式化只能作为条件性独立项目

直接将「FAT16→FAT32→exFAT 全部重写为流式格式化」定义为必做不合理：

1. 当前生成的是**稀疏元数据**，并非整盘数据的逐扇全量初始化；实际元数据体量与卷容量不相等。`SectorDev` 事务的原内容镜像仍占 touched 扇区的 O(N) 空间，即使生成器是 O(1) 流式，也不能宣称整个事务 O(1) 内存。
2. FAT16/FAT32 的主/备 FAT、根目录、FSInfo 与 exFAT 引导区 checksum、FAT、bitmap、upcase/root 必须按原语义逐扇一致；物理 SM4 变换及验证镜像也不能跳过。
3. 流式写盘使应用从「写盘前已完全生成并验收」变成「执行期间才决定内容」，若将生成错误与设备错误混合，会提高中间态风险。
4. 多分区、加密模式、恢复后重初始化和稀疏镜像导出必须具有统一、可回放、稳定的数据源；不支持的模式不得借重构顺势扩展。

**启动条件**：S1 证明真实且已支持的用户卷存在显著内存或规划耗时瓶颈，且先完成可随机访问、确定性的只读 `FormatSectorSource` 原型（可完整 materialize、hash、diff；在首次介质写之前冻结 metadata）。

**验收门槛**：与旧实现的每个生成扇区、范围、导出影像、加密/解密、文件系统验证完全一致；保留预检、所有 touched 原内容镜像、阶段提交、同步和逐扇读回；边界与异常路径验证齐全。未满足则保留现有 BTreeMap 构造，不应为节省少量内存引入全套流式复杂性。

## 8. 统一质量门禁

每项生产代码改动：`git status/HEAD/log` → 最小代码变动 → `cargo fmt --all` → `scripts/test-fast.sh` → `uv run --locked python scripts/test-full.py --profile full --deadline-seconds 900` → `uv run --locked python scripts/audit-redundancy.py --check` → 虚拟磁盘 HIL 与 Rust CI **同一最终 commit SHA** 通过 → 小步提交与 push。真实 USB 写入属于独立、有显式授权的验收阶段，不由此计划自动启动。
