# K6 文件级无损迁移 TUI 产品化规范

日期：2026-09-27

状态：**待实现的专项产品规格**。本文件不表示这些行为已经实现。

关联总规范：`audit/ui/UI_REDESIGN_SPEC.md`

适用基线：K6 后端已经进入 v2.5.0；本规范定义其后续 TUI 产品化要求。

## 1. 目的与边界

K6 已具备文件级无损迁移后端能力，但 v2.5.0 的 TUI 仍把它隐藏在制盘计划内部。用户无法在界面中明确判断何时会迁移文件、迁移哪些区域、需要哪个来源密码域、迁移多少文件/字节，以及规划阶段现在正在做什么。

本规范只解决 **K6 在 TUI 中的可发现性、来源密码闭环、计划展示、规划进度、执行反馈和验收**。四个一级 Tab、统一页面骨架、路由、焦点、输入优先级、更多菜单、任务页和通用视觉规则继续以 `UI_REDESIGN_SPEC.md` 为准。

若两份文档在 K6 相关交互上冲突，本文件优先；实现完成后再把已经落地的规则同步回正式用户文档。

## 2. 产品定位与命名

K6 **不是新的制盘模式**，也不是新的盘型。制盘目标仍只有 mode0、mode1、mode2、mode3、普通盘。

K6 是“当前盘 → 目标盘型”过程中由规划器自动决定的一种数据处置方式，其核心计划语义是 `RegionDisposition::Migrate`。

面向用户统一使用：

- 主名称：**文件级无损迁移**；
- 技术标识：**K6**；
- 推荐组合：`K6 文件级无损迁移`。

禁止新增“mode4”“K6 模式”“迁移模式”等会让用户误解为新盘型的入口。

## 3. 用户必须能回答的四个问题

只要本次计划含 `Migrate`，界面必须让用户在写盘前直接回答：

1. 源盘是什么类型，目标是什么类型？
2. 哪些区域保留、迁移、重新封装、重建或删除？
3. K6 将迁移多少文件、多少字节，是否需要来源密码？
4. 来源读取、暂存、目标文件系统构建和预验证是否已经成功？

不能要求用户通过日志、原始 LBA 或内部结构自行推断。

## 4. v2.5.0 现状审计

### 4.1 已具备

后端已经具备：

- Plain → EDP；
- EDP → Plain；
- EDP mode → EDP mode；
- 类型化迁移规划；
- 来源文件清单、路径冲突、容量与定位预检；
- 已验证 FileKey 的来源解密读取；
- 完整文件负载暂存；
- FAT16 / exFAT 目标文件系统重建；
- 数据区 → 元数据 → MBR 的原子事务；
- 精确读回与回滚；
- CLI 的 Share / Encrypt 来源密码参数；
- 官方模式 TUI 中的来源密码输入与 `v` 验证；
- 计划页对 `RegionDisposition::Migrate` 的基础“迁移”展示。

### 4.2 当前 TUI 缺口

1. 制盘菜单没有明显的 K6 或“文件级无损迁移”说明。
2. `ProvisionKind::Plain` 的字段构建只生成普通分区字段并直接返回，EDP → Plain 时来源密码字段完全不可见。
3. 进入 Plain 表单时当前逻辑跳过来源密码域探测。
4. 来源密码字段主要由目标 mode 决定，而不是由“源盘真实密码域 + 本次计划是否需要读取该域”决定。
5. 计划页缺少文件数、总字节、源/目标角色、文件系统、密码验证状态和迁移预检结果。
6. 几千文件的规划阶段可能明显耗时，但界面没有 K6 类型化进度。
7. 执行页和结果页没有把 K6 作为一等业务阶段持续展示。

结论：**v2.5.0 的 K6 后端已经完成，但 TUI 产品化尚未完整闭环，尤其 EDP → Plain 不能视为完整 TUI 支持。**

## 5. 总体交互原则

### 5.1 自动规划，不增加手工算法开关

用户选择目标盘型、布局、密码和格式化参数；规划器根据源盘与目标自动给出 `PreserveOpaque / PreserveVerified / RewrapVerified / Migrate / Rebuild / Drop`。

UI 不提供“强制 K6”“关闭 K6”“手工迁移此分区”之类开关，不允许绕过 application 层规划结论。

### 5.2 只展示真实证据

- 文件数和字节数必须来自真实 migration manifest；
- 来源密码状态必须来自只读探测/验证结果；
- 文件系统必须来自实际解析或目标规划；
- 无法确定时显示“未知”或“待规划阶段解析”；
- 不允许用“0 文件”代替“尚未扫描”。

### 5.3 K6 必须贯穿 P2～P7

只要计划中存在 `Migrate`：

- P2 可以提示“可能需要文件级迁移”，但不能提前伪造文件数；
- P3 必须展示来源数据与来源密码域；
- P4 必须有独立 K6 数据处理区；
- P5 必须再次汇总迁移规模与密码状态；
- P6 必须显示 K6 执行阶段；
- P7 必须显示迁移与读回校验结果。

## 6. 与总 UI 流程的整合

沿用总规范：

```text
P0 目标选择
  → P1 保存现状
  → P2 选择模式
  → P3 参数配置
  → P4 计划预览
  → P5 写盘确认
  → P6 执行
  → P7 结果
```

K6 不新增平级一级页面。

P2 的模式说明增加“数据处理将自动判定保留 / 文件级迁移 / 重新封装 / 重建 / 删除”。完整 plan 前只能显示“可能需要文件级迁移”，不能提前声称具体文件数。

P3 统一顺序：

1. 来源摘要；
2. 来源数据与密码域；
3. 身份信息（官方目标适用）；
4. 目标分区布局；
5. 目标密码域（官方目标适用）；
6. 格式化；
7. 密码策略。

P4 在“当前→目标变化”之后增加固定“数据处理”区。P5～P7 必须继续展示 K6，不能在计划页之后消失。

## 7. 来源密码域必须由源盘驱动

这是本次最重要的语义修正。

### 7.1 显示规则

来源密码字段由 **源盘真实密码域 + 本次计划是否需要读取该域** 决定，不再只按目标 mode 决定。

- 源盘不存在 Share 域：不显示 Share 来源密码。
- 源盘不存在 Encrypt 域：不显示 Encrypt 来源密码。
- 存在密码域但本次只允许 `PreserveOpaque` 且不读取 payload：可显示状态，但不强制输入。
- 本次 `Migrate` 需要读取加密 payload：必须获得已验证来源密码知识，否则计划阻止。
- 默认密码已经通过验证：显示 `✓ 默认密码已验证`。
- 用户输入来源密码并按 `v` 验证成功：显示 `✓ 用户密码已验证`。
- 未知：显示 `⚠ 来源密码未知`。
- 空输入框绝不能等价于“无密码”。

### 7.2 EDP → Plain

普通盘目标必须补齐完整来源凭据能力：

- 选择 Plain 后仍执行来源 key-domain probe；
- Plain P3 在普通分区配置之前显示“来源数据与密码域”；
- 显示所有真实存在且可能被读取的 Share / Encrypt 来源域；
- `v` 继续验证当前来源密码字段；
- Plain 目标没有 target password，但 source password 不能因此消失。

示例：

```text
来源：disk4 · mode3 内外网通用双分区

来源数据与密码域
交换区   exFAT   来源密码 ********   ✓ 默认密码已验证
保密区   不存在

目标普通分区
P1       LBA 2048   7.50 GiB   exFAT   K6PLAIN
```

### 7.3 Plain → EDP

Plain 源盘没有 EDP 来源密码域，不展示空的来源密码输入框。用户只设置目标 mode 所需 target password。

### 7.4 EDP → EDP

来源密码和目标密码必须视觉分离：

```text
交换区来源密码   ********   ✓ 用户已验证
交换区目标密码   ********
```

禁止用一个“密码”字段同时代表旧密码与新密码。

## 8. P3 来源数据摘要

完整 plan 前只显示已经由只读探测得到的信息：

```text
来源：disk4 · mode3 内外网通用双分区
启动区   FAT16   10.45 MiB
交换区   exFAT    7.49 GiB   读取加密数据需要来源密码
```

文件系统尚未解析时显示“待规划阶段解析”，不能显示“0 文件”。

## 9. P4 K6 数据处理表

规划完成后，TUI 必须直接消费 application 层返回的类型化计划与 migration manifest，不在 TUI 重新解析磁盘或重新计算 disposition。

### 9.1 顶部摘要

只要存在 `Migrate`：

```text
K6 文件级无损迁移
3002 文件 · 120.62 MB · 来源读取与暂存已完成
```

### 9.2 数据处理表

建议最少列：

| 来源 | 目标 | 处理 | 文件 | 数据量 | 文件系统 | 来源密码 |
|---|---|---|---:|---:|---|---|
| Share | Share | K6 迁移 | 3002 | 120.62 MB | exFAT → exFAT | 已验证 |
| Boot | Boot | 重建 | — | — | FAT16 → FAT16 | 不适用 |

处理列必须来自 typed disposition：

- PreserveOpaque / PreserveVerified → `保留`；
- RewrapVerified → `重新封装`；
- Migrate → `K6 迁移`；
- Rebuild → `重建`；
- Drop → `删除`。

技术详情可进一步展示迁移 transform、source/target role、source/target filesystem、manifest 文件数/逻辑字节数、来源凭据状态、暂存预算、目标逻辑预算和目标文件系统预验证状态。

### 9.3 “重建文件系统”与“丢失文件”必须分开

如果 K6 先新建目标 exFAT，再把来源文件迁入，用户看到的必须是：

```text
交换区：重建目标 exFAT + K6 文件迁移（3002 文件）
```

不能只写“交换区：重建”，否则会误导用户以为文件会被清空。

## 10. Planning 阶段需要 K6 类型化进度

真实盘文件较多时，P3 → P4 可能明显耗时。不能只显示“正在规划”。

建议 application/task 层增加类型化进度事件，至少覆盖：

1. `ProbeSource`：识别来源与密码域；
2. `Inventory`：扫描来源文件系统；
3. `StagePayload`：读取 / 解密 / 暂存文件；
4. `BuildTargetFilesystem`：构建目标 FAT16 / exFAT；
5. `VerifyTargetFilesystem`：目标文件系统与 payload 预验证；
6. `PlanReady`：最终写入计划就绪。

有总量时：

```text
正在暂存来源文件… 1240 / 3002 文件 · 48.2 / 120.6 MB
```

无总量时只显示真实阶段和已处理量，不伪造百分比。

规划期间允许切一级 Tab；返回制盘页后恢复同一 operation/generation。修改目标、模式或影响迁移的字段后，旧计划与旧进度结果必须失效。

## 11. P5 写盘确认

只要存在 K6：

```text
目标：disk4 · mode3
K6 文件迁移：3002 文件 / 120.62 MB
来源密码：交换区已验证
目标文件系统：预验证通过
写前备份：已完成
```

确认页必须明确告诉用户：**文件会被迁移，不是简单格式化后丢弃。**

继续沿用精确 YES、安全目标固定和 reopen 身份复核，不新增任何绕过入口。

## 12. P6 执行页

执行页至少区分：

```text
✓ 写前备份
✓ 卸载/锁卷
✓ 重新打开并复核目标身份
● 写入 K6 文件数据
○ 写入协议元数据
○ 提交 MBR
○ 精确读回验证
```

如果后端能够提供文件/字节写入计数，显示真实值；如果只能提供 sector 级事件，就显示 sector 级真实进度，不通过猜测转换成文件数。

详细日志可展开，但主要状态必须来自类型化事件，不通过匹配日志文本决定颜色或阶段。

## 13. P7 结果页

成功时示例：

```text
制盘成功 · mode3
K6 文件迁移：3002 / 3002 文件
迁移数据：120.62 MB
目标 payload 读回：通过
事务读回：通过
```

失败必须区分：

- 规划失败，未写盘；
- 来源读取失败，未写盘；
- 写入失败且回滚成功；
- 写入失败且回滚未完成；
- 目标文件系统后验证失败；
- 最终状态未知。

只有真实证据支持时才能写“文件完整”“已恢复原状”。

## 14. Plain 目标的 UI 修正清单

实现时至少修改以下语义：

1. `ProvisionKind::Plain` 不再在字段构建时只生成目标分区后立即结束；应根据 source probe 追加来源密码域字段。
2. 选择 Plain 后不能跳过来源 key-domain probe。
3. `provision_visible_fields()` 的 Plain 分支同时展示来源密码状态与目标普通分区。
4. 来源密码的 `v` 验证在 Plain 目标继续可用。
5. `PlainProvisionRequest.key_domains` 继续使用同一份 TUI 来源凭据，不再出现“后端支持但 UI 不可输入”的状态。
6. Plain → EDP 与 EDP → Plain 使用同一来源凭据模型，不复制第二套密码状态机。

## 15. 数据模型与单一事实源

建议新增/补充 TUI 只读投影，而不是让 renderer 直接解析迁移内部结构：

```text
MigrationUiSummary
  has_migration
  file_count
  logical_bytes
  rows[]

MigrationUiRow
  source_role
  target_role
  disposition
  source_fs
  target_fs
  file_count
  logical_bytes
  credential_state
  preflight_state
```

名称可按项目实际架构调整，但必须遵守：

- disposition 来自 application/provision；
- 统计来自 manifest；
- credential state 来自 source probe / verify；
- UI 不重复实现 K6 规划算法；
- 密码明文不进入可复制摘要、Debug、日志、任务历史或截图夹具。

## 16. 与总规范的接口

`UI_REDESIGN_SPEC.md` 负责四一级 Tab、P0～P8 路由、页面骨架、输入/焦点/Tab/Esc、通用确认/任务/日志/结果页、响应式布局和统一安全交互。

本规范负责 K6 可发现性、来源密码域规则、Plain 目标来源密码补齐、迁移摘要与数据处理表、planning 类型化进度、执行/结果表达、专项测试与实盘验收。

不得把两份文档实现成两套相互独立的制盘 UI。

## 17. 测试门禁

### 17.1 状态与字段

必须覆盖：

- [ ] EDP → Plain 时 Plain 表单可见真实来源密码域；
- [ ] Plain → EDP 时不显示不存在的来源 EDP 密码域；
- [ ] EDP → EDP 同时区分来源密码与目标密码；
- [ ] 默认密码已验证与用户密码已验证显示真实状态；
- [ ] Unknown 不会被显示成“无密码”；
- [ ] 修改来源密码后旧 verified 状态立即失效；
- [ ] 修改影响计划的字段后旧 migration summary 立即失效。

### 17.2 计划展示

构造至少以下测试情形：

- [ ] 无 Migrate，仅 Preserve；
- [ ] 单 Share → Share Migrate；
- [ ] Plain → EDP；
- [ ] EDP → Plain；
- [ ] 一个区域 Migrate + 一个区域 Rebuild；
- [ ] Drop；
- [ ] RewrapVerified；
- [ ] manifest 统计不可用的 fail-closed 情况。

断言：

- [ ] 只有真正 Migrate 时显示 K6 badge；
- [ ] 文件数/字节数与 manifest 一致；
- [ ] “重建目标文件系统 + K6 迁移”不会被渲染成单独“重建”；
- [ ] 来源密码未验证而计划需要读取 payload 时必须显示阻止原因。

### 17.3 事件与进度

- [ ] K6 planning 事件按 generation 绑定；
- [ ] 切 Tab 后事件仍回到原 operation；
- [ ] 旧 generation 不能覆盖新目标/新参数；
- [ ] 无总量阶段不显示虚假百分比；
- [ ] worker 不直接写终端；
- [ ] 密码不进入事件文本。

### 17.4 回归门禁

- [ ] `cargo fmt --all -- --check`；
- [ ] `scripts/test-fast.sh`；
- [ ] `python3 scripts/test-full.py --profile full`；
- [ ] 受影响的 TUI、provision、migration、transaction 专项测试；
- [ ] 不删除或弱化现有 write safety 断言。

## 18. 真实盘验收

UI 重构完成后，K6 仍需单独做真实硬件验收，不能只看截图或合成状态。

至少覆盖同一授权测试盘：

1. EDP → Plain：在 TUI 输入/验证来源密码，完成规划；
2. P4 能看到真实文件数/字节数；
3. 完成写盘并由操作系统挂载 Plain；
4. 对全部文件做 SHA-256；
5. Plain → EDP；
6. 对隐藏 EDP 目标区域做 raw 解密读取与全量 SHA-256；
7. 前后 aggregate SHA-256 一致；
8. 检查写前备份、readback、rollback 安全链没有因 UI 改造被绕过。

已有 v2.5.0 实盘证据可作为后端基线：3002/3002 文件、120,615,912 bytes、聚合 SHA-256 `8687837a8727e6820fa14a3d1db33d330982037036662b1f742000a5a965e56d` 前后完全一致。新的 UI 验收要证明的是 **同一后端能力可以完整从 TUI 到达**，不是重新发明或重新证明 K6 算法。

## 19. 实施顺序

1. 先修来源凭据模型：Plain 也执行 probe，字段按源盘驱动；
2. 补状态与回归测试；
3. 把来源数据与来源密码域并入 P3；
4. 建立 migration summary 只读投影；
5. 重做 P4 数据处理表；
6. 增加 K6 planning 类型化进度；
7. 接 P5/P6/P7；
8. 做响应式与视觉收口；
9. 跑 fast/full；
10. 最后做真实 USB TUI round-trip。

## 20. 完成条件

只有同时满足以下条件，才能把“K6 TUI 产品化”标记完成：

- [ ] K6 在制盘流程中可发现；
- [ ] EDP → Plain 可从 TUI 完整输入/验证来源密码并完成迁移；
- [ ] Plain → EDP 与 EDP → EDP 行为一致；
- [ ] P4 显示真实迁移统计；
- [ ] P5/P6/P7 不丢失 K6 上下文；
- [ ] planning 有类型化进度；
- [ ] 计划与 UI 都 fail-closed；
- [ ] fast/full 与专项门禁全绿；
- [ ] 真实 USB TUI round-trip 全量 SHA-256 通过；

## 21. 给实现 AI 的直接任务说明
