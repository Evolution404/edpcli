# edpcli 版本及发布生命周期约定

> 生效分支：`feat/multi-logical-sector-20261009`。现行稳定基线：`v2.6.0`（`b0ab82e`）；下一正式目标：`v2.7.0`。不修改或重打已发布标签。

## 版本号及优先级

统一由 `Cargo.toml` 的 `package.version` 管理，`Cargo.lock` 同步。采用语义化版本号，当前功能分支为 `2.7.0-alpha.0`：

| 阶段 | 示例 | 转换要求 |
|---|---|---|
| 已发布稳定版本 | `2.6.0` | 对应唯一的已验证标签 `v2.6.0` |
| 日常功能开发 | `2.7.0-alpha.0` | 每次 Git 提交不增加版本序号；由 SHA 精确识别 |
| Alpha 里程碑 | `2.7.0-alpha.1` | 可选预发布版本；仅在已完成可复现阶段验收后打标签 |
| Beta 测试 | `2.7.0-beta.1` | 主要功能已完成，集中进行跨平台与兼容验证 |
| 发布候选 | `2.7.0-rc.1` | 冻结范围，完成旧 512B 全功能回归、虚拟及授权实盘验收 |
| 正式发布 | `2.7.0` | 全量测试门禁通过，在 `main` 上发布唯一正式标签 |
| 稳定维护修复 | `2.6.1` | 从稳定线派生，严禁混入 2.7 新功能 |

## 源码版本、构建通道与 Git 版本指纹

- `edpcli --version` 继续保持脚本兼容的单行 `edpcli X.Y.Z`；`edpcli version` 使用 Cargo 版本并显示 `STABLE/DEV`、平台、构建目标、编译时间、Git SHA、当前构建分支及工作树状态。
- **Stable 判定必须严格：** 无预发布后缀、构建时 Git 工作树干净，并且 `HEAD` 恰好具有 `v{Cargo版本}` 标签。其余均为 `DEV`；`--release` 只是优化级别，不代表稳定发布。
- 不允许将工作树未提交修改误报为已发布二进制。`Git` 字段需标记 dirty，构建时 `git status` 取证；Git HEAD、索引及跟踪文件变更需要触发 Cargo 构建元数据重算。
- 本地 `make install` **继续编译并安装当前工作树**，不自动联网、不切换分支、不修改 Git。安装前打印工作树分支、Cargo 版本和 SHA，存在本地修改时给出警告。
- `make version` 查看源码当前版本和 Git 状态；禁止通过 `make install` 隐式将工作区切换到稳定标签。
- 当用户希望固定稳定二进制时，应选择官方 Release 产物，按 SHA-256 核验后安装；开发安装与稳定安装的区别以版本通道和 SHA 明确区分。

## 发布审核与不可破坏的行为约束

- 正式发布必须验证版本号与标签一致、无预发布后缀、工作树干净、对应 SHA 唯一，完整测试、Clippy、协议金标、虚拟磁盘 HIL 及目标平台构建均绿；涉及实体盘写入时必须通过授权真机验收。
- 预发布不得替换稳定标签、不得声称已实现计划中仍标为受阻的功能。
- 更改版本管理不得修改官方协议算法、已验证的 512B 读写事务、安全写盘门禁、历史 EDPB、已有 TUI 快捷键及错误处理。
- 开发分支中的 `2.7.0-alpha.0` 不具备 4K 写盘授权。仅完成 P1–P3 只读部分，后续按 `MULTI_LOGICAL_SECTOR_SUPPORT_2026-10-09.md` 的证据与回归门禁实施。

## 发布操作顺序

1. 冻结 512B/4096B 既有已认证功能与官方证据，准备版本提升提交。
2. 从 Alpha → Beta → RC 采用小步提交、按阶段独立回归；不能因为版本后缀晋级就自动授予新写盘权限。
3. 完成全部发布检查，合入 `main`，提升到 `2.7.0`，由审核后的 HEAD 创建不可覆盖的 `v2.7.0` 标签。
4. 发布流水线产出三平台制品、SHA-256、清单、依赖 SBOM；检查制品内嵌 SHA、版本及发布通道。
5. 发生回归：阻止发布，对失败的功能保持禁写，恢复上一稳定制品，不重写已存在的标签。
