# LCE（LBA7 兼容扩展区）

## 1. 状态

LCE 是项目对“LBA7 兼容扩展区”的统一简称。本文记录 LCE 的写入端、物理负载、加解密、消费端和写入边界。

旧项目名称 **区域 A** 已废弃；后续曾使用的 **旧版 type4 扩展区** 也已废弃。官方一方写入端代码已经证明，固定的 `0xC00` 字节物理对象并不专属于 type4。

项目统一术语：

- 元数据表：**LBA7 旧版 EDP 分区表**
- 一方结构体名称：`tagEdpPartionInfo` / `EDP_PARTION_INFO`
- 物理负载：**LCE（LBA7 兼容扩展区）**
- 物理负载大小：`0xC00` 字节 = 3072 字节 = 6 个 512B 扇区
- 当前格式对应结构：LBA12 `tagNewEdpPartionInfo`
- IIR：独立协议对象，不是 LCE

以下写入端结论来自已获取的一方 Windows 制盘链，而不是从盘面样本反推。

### 1.1 闭环矩阵

| LCE 问题 | 状态 | 已验证边界 |
| --- | --- | --- |
| 物理位置/大小 | **完全闭环** | 官方 `CreatePartitions` 由 CHS 派生位置并按 `0xC00` 对齐；LBA7 指针具有最终权威性 |
| LBA7 写入端/指针生成 | **完全闭环** | 官方模式选择 -> `PartionType[]` -> 条目0/后续条目几何 -> LBA7 序列化器 |
| 负载明文 | **完全闭环** | 固定六扇区 FAT16 兼容镜像，3072B |
| 加密/解密 | **完全闭环** | EDPSECDISK zero8 家族 + 物理后端字节偏移修正；Lexar/SanDisk 均可逐字节精确重建 |
| 旧版消费端/挂载 | **完全闭环** | 旧 LBA7 回退路径把条目转换成运行时几何并到达 `EdpMountFile` |
| 驱动物理读写映射 | **完全闭环** | 已挂载虚拟 I/O 通过 `backing_offset + virtual_offset` 映射；完整 `0xC00` 区域均可寻址 |
| 当前正常 LBA12 路径 | **SEPARATE** | 当前正常 type4 挂载不是 LCE，禁止作为 LCE 证据 |
| IIR 关系 | **SEPARATE** | IIR 是另一个独立协议对象 |
| 上层业务触发：谁在何时、为何主动重写 LCE | **OPEN** | 底层可写路径已证明，但决定修改负载的精确业务流程/事件尚未端到端闭环 |
| 所有历史写入端版本是否完全等价 | **OPEN** | 2026 一方写入端已闭环；更早版本仍需独立验证 |

因此，**LCE 的底层生产、定位、内容、加解密、消费和驱动物理写入路径已经闭环；但不能说“所有写入行为 100% 完全搞明白”**。剩余缺口是上层业务触发来源：哪个业务流程在什么条件下决定修改 LCE，以及不同历史版本是否完全相同。

## 3. `PartionType` 官方语义

`edpediskctrl.dll::CEdpDiskControl::InitDiskInfo` 会扫描旧版/运行时分区列表，并设置三个明确的布尔值，由此直接固定数值含义：

| `PartionType` | 一方消费端字段 | 项目中文名称 |
| ---: | --- | --- |
| `1` | `m_bHasBootPart` | 启动区 |
| `2` | `m_bHasSharePart` | 交换区 |
| `4` | `m_bHasEncryptPart` | 保密区 |

这些值已在 `src/protocol/edpf.rs` 中编码为 `EdpPartitionType`。

## 4. 官方制盘模式

原始制盘工具提供四个单选项。原始可执行文件机器码连续绑定了对应界面对象偏移、对象名称和运行时选择器写入。

| 模式 | 官方界面文字 | 写入端 `PartionType[]` |
| ---: | --- | --- |
| `0` | 缺省三分区 | `[1, 2, 4]` |
| `1` | 启动区和交换区二合一 | `[2, 4]` |
| `2` | 整盘加密 | `[1, 4]` |
| `3` | 内外网通用双分区 | `[1, 2]` |

数据路径不会重新映射模式选择器：

1. 制盘工具序列化时把所选模式写入紧凑字段 `+0x34`；
2. `sub_42e8e0` 将其复制到 `LabelInfo+0x7db`；
3. `usbtoolbusmanage.dll::WriteNormalULabel` 将 `+0x7db` 原样复制到注册输入；
4. `cemsusbregsiter.dll::sub_10046e80` 读取同一字节，并展开成上面的四种情况。

`src/protocol/lba7.rs::Lba7PartitionMode` 已固化该矩阵。未知历史序列保持未分类，禁止猜测。

### 4.1 整盘加密模式的特殊规则

模式 2 仍构造兼容序列 `[1, 4]`。写入端随后强制把 type1 配置大小设为 `0x7E00` 字节，并从 type4 中扣除相同大小。界面描述仍说明用户可见模式只包含保密区。因此，在缺少额外证据前，不能把该模式中的 type1 条目描述成普通用户可见启动区。

## 5. 为什么 type2 和 type4 可以指向同一个 3072 字节地址

这是当前最关键的写入端结论。

`CUsbRegsiter::CreatePartitions` **不会**使用同一种几何规则序列化所有旧表条目。

### 5.1 条目0

第一个旧版条目保留第一个逻辑分区的类型和正常逻辑几何。在已观察的写入路径中，它使用正常第一分区起点（`StartSector=63`），分区大小按 63 扇区前缀进行调整。

### 5.2 条目1 和条目2

对后续旧版条目，写入端保留各条目自己的 `PartionType`，但把物理几何覆盖成兼容表示：

- `StartSector` = `sub_10040110()` 的结果；
- `PartionSize` = 按 `0xC00` 字节对齐；
- 在 512 字节扇区介质上恰好等于 6 个扇区。

`sub_10040110()` 使用经典 `DISK_GEOMETRY` 计算地址：

`CHS_geometry_bytes - 0xE0000`

因此，后续条目可以保留**不同的逻辑类型，同时指向同一个物理 3072 字节块**。

这是旧表序列化规则，**不能**据此认定一个逻辑分区是另一个逻辑分区的别名。

### 5.3 各官方模式的结果

模式 0，`[1, 2, 4]`：

- 条目0 type1：正常第一分区几何；
- 条目1 type2：固定兼容扩展区；
- 条目2 type4：同一个固定兼容扩展区。

因此，物理 LBA7 表中 type2 和 type4 具有相同 `StartSector` / `PartionSize=3072` 是预期的一方写入结果。**type2 不是 type4 的别名。**

模式 1，`[2, 4]`：

- 条目0 type2：正常的大交换/二合一分区几何；
- 条目1 type4：固定兼容扩展区。

这解释了真实mode1 SanDisk 配置类型：type2 从 LBA63 开始，而 type4 指向接近 CHS 尾部的位置。

模式 3，`[1, 2]`：

- 条目0 type1：正常第一分区几何；
- 条目1 type2：固定兼容扩展区。

这个一方写入案例直接证明固定物理扩展区**并不专属于 type4**。

## 6. LBA7 序列化

旧表最多包含三个 `0x40` 字节槽（合计 `0xC0` 字节），之后跟随旧版 14 字节密码/状态结构。LBA7 序列化器复制这些字节，应用旧版滚动异或存储变换，然后生成扇区 7 的表示。

类型化解析器位于：

- `src/protocol/edpf.rs`
- `src/protocol/lba7.rs`

固定兼容地址辅助逻辑单独位于：

- `src/protocol/lba7_compat.rs`

这种拆分是有意设计：逻辑分区类型与物理兼容扩展区是两个不同概念。

## 7. 物理扩展区内容与加解密闭环

命名纠正后，此前对物理六扇区块的结论仍然有效：

- 扩展区精确为 3072 字节；
- 已提交的 Lexar 采集和实时mode1 SanDisk 采集，都是其 LBA7 指针位置上的真实物理密文；
- 恢复出的明文是固定 FAT16 兼容镜像；
- 使用 zero8 密钥的旧版 EDPSECDISK 变换，加上物理后端字节偏移修正，可以逐字节精确重新生成已验证设备密文。

这些事实描述的是负载字节，并不改变写入端结论：同一个物理对象可以根据条目位置和官方模式被 type2 或 type4 引用。

标准测试夹具位于：

`audit/protocol/lba7_compatibility/`

字节账本无缺口覆盖完整 `+0x000..+0xBFF`。

## 8. 消费端边界

历史 `EdpEDiskCtrl` 可以从首选新标签路径回退到旧版 LBA7 表，把旧条目转换成运行时形式，再把其后端几何提交给旧版虚拟磁盘路径。因此旧驱动能够把主机虚拟写入映射到物理 LCE。

这证明存在有条件的消费/写入路径，但不代表每块盘或每次登录都会进入该回退流程。

当前正常 LBA12 路径使用另一套独立几何来源，禁止把它引用为“LCE 就是当前 type4 文件系统分区”的证据。

## 9. IIR 与 LCE 相互独立

IIR 相关实现保留在 `src/protocol/iir.rs` 和 `tests/iir.rs`。

LCE 与 IIR 是不同协议对象。此前把旧称“区域 A”绑定到 IIR 的尝试不属于当前模型。

## 10. 版本适用范围

四模式写入矩阵目前只对上文已识别的 2026 一方 Windows 栈成立，不能自动投射到所有历史制盘工具版本。

在声称各年代都使用完全相同的界面模式矩阵和条目几何规则前，必须分别检查更早写入端二进制。

一方代码公开了结构体名称和字段语义，但没有找到给 `0xC00` 负载对象命名的独立符号。因此 **LCE / LBA7 兼容扩展区** 是项目自定义描述性术语，不宣称它是厂商原始符号。

## 11. 当前协议不变量

仓库把以下规则作为回归不变量：

1. `PartionType=1/2/4` 分别表示启动区/交换区/保密区。
2. 官方模式 0/1/2/3 分别映射到 `[1,2,4]`、`[2,4]`、`[1,4]`、`[1,2]`。
3. LBA7 模式分类必须精确；未知序列不得猜测。
4. 3072 字节兼容指针由旧版条目位置/几何决定，不要求 `PartionType=4`。
5. 多个后续条目可以在保留不同逻辑类型的同时指向同一个兼容扩展区。
6. LBA7 指针具有最终权威性；CHS 公式只作为独立写入端交叉验证。
7. IIR 保持独立模块和独立证据链。


## 12. 原生4Kn来源重放的指针校验（2026-10-09）

离线来源重放必须明确区分两种几何：

- `LBA12` 记录负责当前逻辑分区的真实起点与容量；
- `LBA7` 第一个旧版记录描述第一分区，后续记录负责统一指向物理兼容扩展区。

`NativeEdpLayoutPlan::verified_source_replay_native_blocks` 已增加二次来源绑定：
所有后续 `LBA7` 条目的 `StartSector` 必须与已确认的 `LCE` 原生起点一致；
记录的 `PartionSize` 必须等于占用的完整原生块数乘以设备块大小。
传统512B为3072B，原生4096B时一个完整块占4096B。
这里校验的是**完整物理占用**，不是将3072B的历史明文负载强行解释成一个3072B的4Kn物理块。

测试将四种官方模式的合成原生来源统一编码这一关系；只篡改第二个或后续旧版条目的指针/大小，即使 `MBR` 与 `LBA12` 不变，也必须拒绝严格重放。
旧版仅校验首分区的重放接口保留用于显式的隔离测试，不应作为来源认证结论。

**尚未闭环：** 本批没有对原生4Kn兼容扩展区的完整4096B密文建立独立密码学金标；尾部1024B的所有者和生命周期仍需原生来源及消费端证明。
这类来源重放是只读证据保留，不授权实体制盘或恢复。

## 13. 离线来源读取与真实物理块溯源门禁（2026-10-09）

已有 `LBA7` 指针认证和虚拟重放后的逐块回读校验不能自行证明输入 `source_lce` 就取自来源介质的正确位置：调用方可以错误地将另一份同宽度缓冲区传入。为降低这类失配风险，新增 `NativeEdpLayoutPlan::verified_source_replay_from_reader`：

1. 用同一个**只读**原生扇区回调获取来源 `LBA0..12` 的完整块，并建立原生协议镜像；
2. 校验 `EDPF` 身份和分区布局、全部后续 `LBA7` 兼容扩展区指针，再单独校验 `MBR` 首分区；
3. 只在上述条件全部成立后，按指针确定的原生扇区地址读取完整 `LCE` 块；4Kn为一个4096B块，512B为六个512B块；
4. 用完全相同的来源块生成虚拟重放计划，保留4Kn尾部非拥有字节。读取失败、缺失、错位、短块均拒绝。

该调用顺序避免常见的**无意拼接错误**。输入回调本身仍不具备密码学真实性证明：同一回调可能被恶意替换，因此不能称作独立认证了完整 `LCE` 密文内容。旧的数据变换金标和实体写保护不因此改变。

## 14. U391 原生4Kn：**位置已闭合，不等于4096B负载已闭合**（2026-10-09）

### 指针与官方定位：三方吻合

在实体 U391（VID:PID `3535:0901`，原生4096B，物理长度255944818688B，共62486528个原生块）上，先独立复核USB设备身份、几何、LBA7/LBA12 EDPF、Mode0分区，再只读获取LBA7两个后续条目。交换区type2与保密区type4的两个独立指针同为 `StartSector=62476561, PartionSize=4096`。

官方`CUsbRegsiter::CreatePartitions/sub_1003DB50`对后续LBA7条目调用`sub_10040110`，计算`CHS_bytes - 0xE0000`，将历史`0xC00`按设备原生大小上对齐。U391独立计算：

- `3889柱面 * 255磁头/柱面 * 63扇区/磁道 * 4096B = 62476785 * 4096B`；
- `0xE0000 / 4096 = 224`原生扇区；
- `62476785 - 224 = 62476561`；
- `ceil(3072 / 4096) * 4096 = 4096B`。

因此**原厂CHS算法、LBA7 type2指针、LBA7 type4指针三者对地址/占用长度吻合**。这只证明该位置被预留为旧版兼容区，并不证明物理字节已被某个4Kn LCE生产者正确初始化。

### 指针前后与加密分区的反例

严格只读扫描：`LBA62476529..62476593` 连续65个原生块（每块4096B）均为非零高密度内容，其中LCE指向块含4037个非零字节，前后邻居通常4035–4048个非零字节。每个块均可划分为8个512B子框；**所有520个子框**在帧内偏移`0,5,6,7,256`均为零，且帧内偏移`8`在所有子框均非零。此固定结构同样贯穿所指原生块的最后1024B（两个512B子框）。

校验对照：

| 采样类别 | 固定零帧内偏移0/5/6/7/256 | 典型4096B零字节数 | 状态 |
| --- | --- | --- | --- |
| 指针前32块 | 32/32每块8个512B子框均满足 | 53.97（平均） | 与指针同构 |
| 指针本身4096B | 8/8满足 | 59 | 与邻居同构 |
| 指针后32块 | 32/32每块8个512B子框均满足 | 53.66（平均） | 与指针同构 |
| 当前交换区加密起点 | 无固定零子框模式 | 14.50（4块平均） | 不同 |
| 当前保密区NTFS起点 | 无固定零子框模式 | 12.00（3块平均） | 不同 |
| 当前保密区MFT | 无固定零子框模式 | 12.50（2块平均） | 不同 |
| 历史Lexar/SanDisk 512B LCE金标 | 不具有上述全512B帧的共性 | 不作4096B外推 | 不同 |

更加宽的有界抽查显示这种固定512B子框模式至少在LCE前256个原生块及指针后95个块连续出现；指针后+96..+220为混合非零/零/同构块，指针后+221..+256为全零。因此U391该位置看起来嵌在一片*独立于现存加密分区数据格式*的结构化保留区域中，而非一个可独立证明的3072B密码学负载；末尾1024B**没有可观察的语义结构边界**。这不能排除旧版LCE元数据后来曾写入其中，也不能证明此区域没有真正的其他所有者。

旧版官方 `zero8+a7f0_full`以真实4Kn物理偏移重造前3072B，与来源有3061/3072字节不同；以错用512B偏移重造则3062/3072字节不同。使用旧驱动`a6b0_full`分别以真实4096B、旧512B、零及两个平移偏移解密4096B后，头3072B与尾1024B均不产生明确FAT/NTFS结构；加密/解密能往返仅证明变换自洽，**不证明解出有效LCE数据**。

### 原厂生产者职责边界与设计约束

- `CreatePartitions` 可独立证实的是 **LBA7/LBA12几何/标记/密钥记录的写入**。在已审计的一方写入端和旧虚拟驱动中，历史LCE可通过有条件的回退挂载及虚拟卷写入到达物理 `ZwWriteFile`；**尚无本次4Kn实盘写入事件/独立金标，不能从其地址推定产生本次4096B数据的函数**。
- U391源块`+0..3071`未被证实是旧版固定FAT16兼容负载；`+3072..4095`未被证实是padding或独立追加元数据。唯一认证的事实是：**完整原生4096B属于LBA7记录指向的物理范围**，最后1024B跟前3072B分享与邻居相同的512B子框特征。
